# Contract: Module-CR Handling

## Scope

This document defines the behavioral contract for `Lifecycle-Manager` (LM) with respect to the `Default-Module-CR` and the `Module-CRD` on an SKR cluster.

It covers:

- The lifecycle of the `Default-Module-CR` on the SKR (create, delete, non-reconciliation).
- The role of the `Module-CRD` in the module's resource set, including version evolution.
- The interaction between the `Default-Module-CR`, user-created `Module-CRs`, and the deletion gate.
- The scope selection between namespace-scoped and cluster-scoped `Module-CRD`.

It does **not** cover:

- Mandatory Modules — they follow a different code path and do not have a `Default-Module-CR` (see [DL01](#decisions-references)).
- Community modules — not installed by LM.
- Market-specific `Module-CRs` — multiple `Default-CRs` per market are out of scope.
- Business status reporting for a module instance — LM tracks installation state only (see R090).

## Decisions

The items below are in effect. Each item is backed by a decision reference. When an item can be resolved by a combination of an ADR and a GitHub issue, the ADR is listed first.

| ID   | Description                                                                                                                                                                                | References     | Comments                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| R010 | LM creates the `Default-Module-CR` in the SKR only if the module's `CustomResourcePolicy` is `CreateAndDelete`.                                                                            | DL01, DL03     |                                                                                                                   |
| R020 | LM creates the `Default-Module-CR` in the SKR at most once per manage cycle. If the CR is later modified or deleted, LM does not restore it.                                               | DL03, DL08     | Re-managing the module resets the manage cycle: Manifest is deleted and recreated, and the create step runs again. |
| R030 | LM does not actively reconcile the `Default-Module-CR`. After creation, LM never rewrites, re-applies, or updates its spec.                                                                | DL02, DL03     |                                                                                                                   |
| R040 | LM deletes the `Default-Module-CR` (if it exists) during module deprovisioning **only** if the module's `CustomResourcePolicy` is `CreateAndDelete`.                                       | DL02           |                                                                                                                   |
| R050 | For `CustomResourcePolicy: CreateAndDelete`, LM deletes only the `Default-Module-CR`. User-created `Module-CRs` of the same `GroupKind` are not touched.                                   | DL02           | Addendum to DL02 accepted 2025-04-23.                                                                             |
| R060 | Module deprovisioning is blocked until all `Module-CRs` (of the `Module-CRD`'s `GroupKind`, across all namespaces, across all `RESTMapper`-known versions) are removed from the SKR.       | DL02, DL07, DL06 | Applies to both `CreateAndDelete` and `Ignore`. Cross-namespace: DL05. Cross-version: DL04, DL11.               |
| R070 | While the deletion gate (R060) is not satisfied, LM keeps module resources (CRD, RBAC, module operator) up to date in the SKR so that the module operator can process CR deletions.        | DL10           | Two-phase-delete Phase 1. Formal state-machine shape is pending — see PD050.                                       |
| R080 | If the user re-enables a module while its deprovisioning is still in progress, LM continues the deprovisioning to completion before starting a fresh installation.                         | DL10           |                                                                                                                   |
| R090 | LM reports only installation state for a module. Business-level status of a `Module-CR` (readiness, configuration validity, and so on) is owned by the module operator and not surfaced by LM. | DL02           | `Kyma.Status.Modules[].Resource` exposes the tracked `Default-Module-CR` as a `TrackingObject`, not its business status. |
| R100 | All regular (non-mandatory, non-community) modules must provide `Default-Module-CR` data in `ModuleTemplate.Spec.Data`. This is enforced by the module publishing pipeline, not by LM at reconcile time. | DL01 |                                                                                                                   |
| R110 | LM populates `Manifest.Spec.Resource` from `ModuleTemplate.Spec.Data` regardless of `CustomResourcePolicy`, so that the `GroupKind` used by the deletion gate (R060) is always known.       | DL02           |                                                                                                                   |
| R120 | LM applies `Module-CRD` changes verbatim from the module manifest. Adding a new API version is safe. Dropping an API version is not performed by LM today (see PD020).                     | DL09           | ADR 006 covers KCP↔SKR CRD synchronization for LM's own CRDs; it is the closest existing decision for module CRDs. |
| R130 | The `Default-Module-CR` is not tracked in `Manifest.Status.Synced`. It is created and deleted outside the render/prune pipeline.                                                           | DL08           | Prevents the prune pass from ever removing the `Default-Module-CR`; the deletion of the CR flows through R040.    |
| R140 | LM interacts with `Module-CRs` on the SKR via the SKR client only. The KCP client is used solely for Manifest-side operations (e.g. finalizer removal).                                    | DL02           | Design invariant.                                                                                                 |

## Pending decisions

The items below are either open gaps in the design or items where the team has not yet decided the behavior. LM's current behavior in these cases is not authoritative — the intent of listing them here is to make the gap visible and to route the decision through an ADR or an issue. Do not derive requirements from the implementation for the items in this section.

| ID    | Description                                                                                                                                                                                                                                       | References | Comments                                                                                                                                                                                                                                                                                              |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PD010 | LM identifies the `Default-Module-CR` by `name`/`namespace`/`GVK` derived from `Manifest.Spec.Resource`, which is copied from the OCM-artifact-provided `ModuleTemplate.Spec.Data` of the currently-deployed module version.                       | GAP        | No ADR or issue defines this explicitly. The current behavior falls out of the parser. It becomes relevant every time the Module Team changes the shape of `Default-Module-CR` between versions — see PD030, PD040.                                                                                    |
| PD020 | Contract with the Module Team for **dropping** a `Module-CRD` API version safely (avoiding orphaned instances in `status.storedVersions`). Options: per-instance annotation, CRD-level annotation, both, or "module team's responsibility."         | DL14, DL15, DL13 | Kubernetes forbids removing a version from `spec.versions` while it still appears in `status.storedVersions`. LM already implements `DropStoredVersion` for KCP CRDs; no equivalent runs on SKRs today. Team must decide the contract shape before implementation.                                        |
| PD030 | **Scenario A — Module Team renames the `Default-Module-CR` in the next module version** (change of `metadata.name` and/or `metadata.namespace` in `ModuleTemplate.Spec.Data`). What should LM do?                                                  | DL13       | Current behavior: LM's new `Manifest.Spec.Resource` no longer points at the previously-created CR. A new CR is created alongside the old one; on deprovisioning only the new one is marked for deletion, and the old one blocks the deletion gate (R060) indefinitely as a "user CR." Team must decide: reject via validation, support renames with previous-name tracking, or document as a Module-Team constraint. |
| PD040 | **Scenario B — SKR user "renames" the `Default-Module-CR`** by creating a new CR with a different `name`/`namespace` and deleting the original. What should LM do?                                                                                | GAP        | True renaming is not possible in Kubernetes. Interaction with current rules: R030 (no active reconciliation) means the deleted original is not restored; R020 (create-once) means LM does not re-create the `Default-Module-CR`; the new CR becomes a user CR and blocks the deletion gate (R060) on deprovisioning. Team must decide whether this outcome is acceptable, or whether LM should re-create, track, or reject. |
| PD050 | Formalization of the two-phase delete (Phase 1: await CR removal; Phase 2: deprovision resources) as an explicit Manifest state machine with named states and observable transitions.                                                             | DL13, DL10 | The current behavior (three code paths gated on the deletion gate's result) is R060/R070-compliant but not exposed as a state machine. Decide whether an explicit state machine is required.                                                                                                            |
| PD060 | Authoritative signal for **cluster-scoped** `Module-CRD` and where the scope must be enforced. Three signals currently exist and can disagree: the `operator.kyma-project.io/is-cluster-scoped` annotation on `ModuleTemplate`, the SKR `RESTMapper` scope, and the empty-namespace observation on a returned resource. | DL13       | Decide which signal is authoritative and whether enforcement belongs at the parser layer, the client layer, or both.                                                                                                                                                                                    |
| PD070 | Existence of `Default-Module-CR` as a **cluster-scoped** resource. Is this a stakeholder requirement or an accepted side effect of the current implementation?                                                                                    | GAP        | No ADR or issue captures the rationale. Decide whether cluster-scoped `Default-Module-CR` is supported, and record the decision.                                                                                                                                                                        |
| PD080 | LM's behavior when a `Module-CRD` is **not** present in the module's resources (module ships without its own CRD). Treat as error and set the Manifest to `StateError`, or accept and rely on the Module Team to install the CRD by other means? | GAP        | Today LM accepts this configuration. If the CRD is not installed by any means, the `Default-Module-CR` creation fails at the API server.                                                                                                                                                              |
| PD090 | LM's behavior when two different modules ship the **same** `Module-CRD` `GroupKind`. Under R060 each Manifest's deletion gate blocks on the other's CRs, and unblocking order is non-deterministic.                                                | DL02       | DL02 assumes each `Default-Module-CR` belongs exclusively to one module. Decide whether LM must enforce this (rejection, ownership label, disambiguation by owner reference, etc.) or document it as a Module-Team constraint.                                                                        |
| PD100 | LM's behavior for a module marked as **Mandatory** whose module manifest happens to declare a `Default-Module-CR`. Ignore silently, warn, or reject?                                                                                              | DL01       | DL01 states Mandatory Modules should not have a `Default-Module-CR`. The behavior for a misconfigured Mandatory Module is not defined.                                                                                                                                                                 |
| PD110 | Whether to expose the **installed version** on the Manifest status (e.g. `Manifest.Status.InstalledVersion`) and use it for version-scoped queries, instead of iterating all `RESTMapper`-known versions.                                        | DL13       | Related to R060 and R120. Current version-agnostic listing is functional but imprecise; adding installed-version tracking would improve auditability and query cost.                                                                                                                                    |
| PD120 | Evolution of `CustomResourcePolicy: CreateAndDelete` in a world where UI or CLI flows drive module configuration.                                                                                                                                 | DL16       | The current `CreateAndDelete` semantics predate the current UI/CLI direction. Decide whether the policy needs a new variant, is deprecated, or remains as-is.                                                                                                                                            |
